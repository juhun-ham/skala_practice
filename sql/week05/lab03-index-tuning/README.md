# HR 데이터 인덱스 튜닝

직원 50,000건이 저장된 PostgreSQL HR 스키마에서 함수·형변환·와일드카드·정렬·OR 조건이 인덱스 사용에 미치는 영향을 `EXPLAIN (ANALYZE, BUFFERS)`로 비교한 실습입니다. 수치는 동일 쿼리를 5회 실행한 평균이며, 데이터와 캐시 상태에 따라 달라질 수 있습니다.

## 핵심 해석

- PostgreSQL은 Primary Key와 UNIQUE 제약조건에 필요한 B-tree 인덱스를 자동 생성하지만, 외래키와 일반 컬럼에는 자동 생성하지 않는다.
- 인덱스 컬럼에 함수나 형변환을 적용하면 일반 인덱스의 정렬 값을 그대로 이용하기 어렵다. 가능하면 입력값을 컬럼 자료형과 저장 규칙에 맞추고, 쿼리를 바꿀 수 없을 때 표현식 인덱스를 고려한다.
- 특정 도메인만 반복 조회한다면 부분 커버링 인덱스가 작고 빠르다. 여러 도메인 검색이 필요하면 도메인 표현식 인덱스가 더 범용적이다.
- `ORDER BY ... LIMIT`은 인덱스 정렬 순서를 이용할 수 있으면 별도 정렬 없이 필요한 행에서 탐색을 멈출 수 있다.
- OR 양쪽에 사용할 수 있는 인덱스가 있으면 PostgreSQL은 여러 `Bitmap Index Scan` 결과를 `BitmapOr`로 합칠 수 있다.
- `Index Only Scan`도 가시성 정보에 따라 Heap을 확인할 수 있다. `Heap Fetches: 0`이면 실제 테이블 접근 없이 결과를 반환한 것이다.

## 설계 판단

가장 빠른 인덱스를 무조건 추가하기보다 조회 빈도와 쓰기 비용을 함께 고려해야 한다. 인덱스는 저장 공간을 사용하고 INSERT·UPDATE·DELETE마다 유지 비용이 발생한다. 특히 특정 검색값에 종속된 부분 인덱스와 특정 함수에만 맞는 표현식 인덱스는 요구사항이 명확할 때 적용하는 것이 적절하다.
