# E-Commerce DB 쿼리 튜닝

PostgreSQL의 `EXPLAIN (ANALYZE, BUFFERS)`로 쿼리 실행계획을 확인하고, 인덱스와 쿼리 재작성 전후를 비교한 실습입니다. 수치는 실습 데이터와 당시 캐시 상태에서 5회 측정한 평균이므로 절대 성능이 아니라 실행계획 변화와 병목을 이해하기 위한 참고값입니다.

## 관찰한 점

- 인덱스는 존재 자체보다 선택도, 테이블 크기, 쿼리에 필요한 열을 함께 고려해야 한다.
- 큰 조인 전에 먼저 집계하면 이후 단계로 전달되는 행 수와 정렬·집계 비용을 줄일 수 있다.
- 이미 계산된 주문 단위 금액이 있다면 주문상품을 다시 합산하지 않는 편이 효율적이다. 단, `payments`가 주문당 한 행이라는 데이터 규칙을 먼저 검증해야 한다.
- 작은 테이블에서는 Seq Scan이 인덱스보다 합리적일 수 있으며, 1ms 미만 차이는 실행 편차를 함께 고려해야 한다.
- 구조적으로 더 복잡한 튜닝이 항상 더 빠른 것은 아니므로 실제 실행계획과 반복 측정으로 검증해야 한다.

## DBMS 옵티마이저 비교 요약

PostgreSQL, Oracle, MySQL, SQL Server는 모두 통계와 예상 비용을 바탕으로 실행계획을 선택하지만 계획 관리 방식에는 차이가 있다. 이번 실습의 핵심은 특정 DBMS나 인덱스를 무조건 선호하는 것이 아니라, 예상 행과 실제 행, 중간 결과 크기, 버퍼 접근, 정렬·집계 비용을 함께 확인하는 것이다.
